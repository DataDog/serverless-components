# Parity harness

This harness compares the Go `serverless-init` with its Rust replacement by running the same scenarios against both and comparing what each one sends. It is uncommitted work on the `duncan-harvey/unified-agent-rust` branch.

## How to run

Run every command from this directory.

- `go vet ./...` checks the code.
- `go test ./...` runs the unit tests.

## How to build

Run every command from this directory. Binaries are built for Linux and the host architecture, and are written under `out/bin/`.

- `go run ./cmd/parity build go` removes the previous `out/bin/go/datadog-init`, runs the build script of `serverless-init-ci` and copies the Go `serverless-init` there. Next to it, `out/bin/go/BUILD_INFO` records the `datadog-agent` checkout path, its commit and whether it had uncommitted changes, which `record` checks. The script pulls a base image from the public Amazon container registry, so first sign in with the Docker login command for `public.ecr.aws`. Without it, the build fails with a 403 error.
- `go run ./cmd/parity build rust` builds `datadog-init` with `cargo zigbuild` for the musl target and falls back to `cross` if that fails. It copies the result to `out/bin/rust/datadog-init`. `cargo zigbuild` works with the repository's linker settings, so `cross` is not required.
- `go run ./cmd/parity build workload` builds the workload driver to `out/bin/workload/parity-workload`, and the fake Google Cloud metadata server to `out/bin/workload/fake-gcp-metadata`.
- `go run ./cmd/parity build fakeintake` builds the Docker image `parity-fakeintake:local` from the local `datadog-agent` checkout. The Dockerfile needs the checkout root as its build context.

The build script archives the `datadog-agent` checkout under its directory name, and the Dockerfile of `serverless-init-ci` expects that name to be `datadog-agent`. A worktree used for the Go build must therefore be in a directory named `datadog-agent`, for example `~/dd/datadog-agent-parity-reference/datadog-agent`; with any other name, the build fails with `cat: .dda/version: No such file or directory`.

The checkout locations default to `~/dd/datadog-agent`, `~/dd/serverless-init-ci` and `~/dd/serverless-components`. Change them with the flags `--agent-path`, `--ci-dir` and `--components-dir`, or with the environment variables `PARITY_AGENT_PATH`, `PARITY_CI_DIR` and `PARITY_COMPONENTS_DIR`. The flag `--arch` chooses `arm64` or `amd64`.

## How to compare

Run every command from this directory. Each command checks that every scenario's platform file exists, and writes its output to `out/<run id>/`, where the run id is the start time and a random suffix, with one directory per scenario and binary: `out/<run id>/<scenario>/<binary label>/` holds the Compose file, `capture.raw.json` and `normalized.json`. Compose project names are `parity-<run id>-<scenario>-<binary label>`, so two invocations at once don't touch each other's projects. Each command first removes the parity projects that earlier runs left: those whose run directory no longer exists, those whose newest container was created more than the five-minute scenario timeout ago (the creation time `docker ps` reports, not the run id's time, because an invocation can last longer than five minutes), those without a container, and those named without a run id. Scenarios that set `align` or a stop signal, or whose reference has a measurable flush interval or shutdown, run one at a time after the others, so that their timing is not noisy.

- `go run ./cmd/parity run --binary rust` runs every scenario against the binary and compares it with the Go references in `reference/`. `--binary` takes `go`, `rust` (the default) or a path to `out/bin/<label>/datadog-init`; the runner finds the workload driver and the platform files relative to it, so other locations are refused. `--scenario <name>`, given once or more, runs only those scenarios. `--parallel` sets how many scenarios without timing features run at once, 4 by default. The run writes `report.md` and `report.json`, and `<scenario>/diff.txt` for each scenario with differences. It exits with status 1 unless every scenario is pass, expected-only or reported, so a scenario without a reference also gives status 1.
- Each reference records the SHA-256 of the Go binary that recorded it, and of the files it depends on: its scenario file, its platform file, `normalize.yaml` and `compare-defaults.yaml`. `run` gives a scenario the status harness-error, without running it, when its reference names another Go binary than `reference/SOURCE`, or when one of those files changed since it was recorded, for example `the reference of logs.stdout-capture is stale: normalize.yaml changed since it was recorded; run parity record --scenario logs.stdout-capture`. So after changing any of them, record the references again. The reference's timing measures are computed again from its timing input with the current tolerances, so a tolerance change in `normalize.yaml` takes effect after that record too.
- `go run ./cmd/parity record` runs every scenario against the Go binary and records `reference/<scenario>.json`. It refuses when the `datadog-agent` checkout has uncommitted changes, or is at a different commit from `reference/SOURCE`. It also refuses a Go binary whose `BUILD_INFO` is missing, names another commit or a checkout with uncommitted changes, or, without `--repin`, whose SHA-256 differs from the one in `reference/SOURCE`. `--repin` accepts a different commit and a new binary of it, and also removes the references of scenarios that no longer exist; it still refuses uncommitted changes, and cannot be combined with `--scenario`. Every scenario is recorded into `out/<run id>/staged-references/` first. Only when all of them succeed are the files moved into `reference/`, and `reference/SOURCE` is written last with the commit, the SHA-256 of the Go binary and the commit of the fakeintake checkout whose decoders read the payloads (the one `go.mod` replaces the module with), keeping its release line, which a person keeps up to date. A failed record changes nothing in `reference/`. Build the Go binary from that commit first. The enhanced metric `cpu.limit` equals the host's CPU count, so references are machine-specific and must be recorded on the machine that runs them.
- `go run ./cmd/parity stability --runs 5` runs each scenario against Go five times and lists, in `stability.md`, every path and timing measure that varies between any two runs by more than the tolerances in `normalize.yaml`.

Every command also takes `--scenarios-dir`, which defaults to `scenarios/`, and `--components-dir`.

Scenario files are read strictly: an unknown field, an argument that the step kind doesn't read, `then` on a step other than `wait_for_signal`, a sleep that isn't a duration, an exit outside 0 to 255, a `stop` without a signal and an unknown comparator are errors.

Normalizer rules and timing tolerances are in `normalize.yaml`. Comparator overrides that apply to every scenario are in `compare-defaults.yaml`; a scenario's own `compare.overrides` take precedence over them. Each entry in both files needs a reason. A mask rule can set `when_matches: <regular expression>` to mask only the values that match it as a whole; the instance-tag masks use it to hide only Docker container hostnames (12 lowercase hexadecimal characters), so the fixed Google Cloud Run instance ID is still compared. Absolute timestamps are not masked but checked against the run by `relative` rules, such as `relative: {unit: s, align: 10s, lead: 10s}`: a timestamp becomes `in window` when its unit puts it between the agent container's start and exit (with one second of margin, and `lead` more before the start, for a bucket that began before the agent), with `, aligned` when it is a multiple of `align`; otherwise it becomes `out of window: <value>` or `not aligned: <value>`, which differs from Go's label. The units and alignments in `normalize.yaml` are what Go 1.12.0 sends. Series other than `datadog.agent.running` declare `align: 10s`, because they carry 10-second buckets, while `datadog.agent.running` carries the flush time and declares no alignment; a filter in the rule path selects them. Span start times are compared exactly, because they come from the workload's fixtures.

The normalizer and the comparator use two path languages. A normalizer path reaches values to change: `series[].tags[instance]` is the value of every `instance:` tag of every series, and a filter `[field=value]` or `[field!=value]` keeps the objects of a list whose field equals, or does not equal, the value, as in `series[metric!=datadog.agent.running].points[].timestamp`. A compare path names a combined item and a field of it, and `*` matches any run of characters other than `]`: `sketches[metric=datadog.serverless_agent.enhanced.cpu.usage,*].sum` is the sum of that metric's sketches with any tags. The Go agent sends traces in the indexed (v1) format, which the normalizer converts into the legacy span form, so that a binary that sends v0.4-style payloads compares in the same form; a payload it can't convert is listed as undecoded and fails the scenario.

A scenario without a stop signal has a deadline: when the agent is still running 20 seconds after the workload's last step, the harness sends it SIGTERM, then SIGKILL after 15 seconds, captures the run anyway and reports the difference `process.not_exited`, for example `the agent did not exit within 20 seconds after the workload finished`. An agent killed 15 seconds after the stop signal gets `the agent did not exit within 15 seconds after the stop signal`. The report shows a row `Killed with SIGKILL` when either run was killed. The workload's HTTP requests time out after 5 seconds.

The harness sends a scenario's stop signal `stop.after_seconds` after the workload's step clock started, which the driver records in its event log as `clock_started`, so the distance from the last step to the signal doesn't depend on the binary's startup time. Without that event, it times the signal from the container start. The stop time used by the timing check is that send time, converted to the Docker clock with an estimated offset, or the driver's own event of the stop signal when that is up to 100 milliseconds earlier: the estimate can otherwise put a fast exit, such as Go's 40-millisecond shutdown, before the signal. In sidecar mode, when the agent exits before Docker can start the workload container, which joins the agent's network namespace, the run goes on without the workload instead of ending in a harness error.

A scenario with `align: {every: 10s, offset: 500ms}` runs at a fixed phase of the wall clock: the harness starts fakeintake, reads the Docker clock in it, then starts the agent one second before an aligned moment of the Docker clock (500 milliseconds after a multiple of 10 seconds since the Unix epoch), and the workload, which uses the Docker clock, starts its step clock at that moment. When Docker reports that the agent container started after that aligned moment, the run is a harness error that names the delay, for example `the agent container started at ..., 200ms after ..., the aligned moment the workload's step clock was to start at`. When the workload's step clock starts after that moment, the workload has waited for the next one, 10 seconds later, and the run is a harness error too. Go puts DogStatsD points into 10-second buckets aligned to the wall clock and flushes them at 3-second ticks that start with the agent, so without align the metric delays and intervals vary by up to 5 seconds between runs; with it they vary by under 50 milliseconds. The timing scenarios set it.

A flush interval is the median gap between flushes, and needs at least three flushes; with fewer it is not measurable. The flush interval of an area (`timing.interval.<area>`) is measured on the payloads that carry at least one item the workload sent, so the agent's own metrics, which arrive at every flush, can't hide a slower flush of the workload's. A second measure, `timing.flush_interval.<area>`, takes every payload of the area: Go's DogStatsD metrics arrive with its 10-second buckets whether it flushes every 3 or every 10 seconds, so the agent's own metrics are what show its flush interval. Check runs are a timing area too: the workload never sends one, so only `timing.flush_interval.check_runs` is measured, which catches an agent that sends `datadog.agent.up` once instead of at every flush. A scenario can set `coverage_gap: <reason>` when it can't yet check all of what its name says; the report marks it, and the parity bar line counts it, for example `P0 scenarios passing: 20 of 20 (2 with known coverage gaps)`. A scenario with `report_only: true` is measured and reported, never passes or fails, and is left out of the parity bar.

Scenario files are in `scenarios/`, one per scenario, and each file name is the scenario name followed by `.yaml`. Platform environment files are in `platforms/`. Generated output goes to `out/`, which git ignores.

## Platforms

A scenario's `platform` names a file `platforms/<platform>.env` of `KEY=VALUE` lines, which every container of the scenario receives before the intake variables and the scenario's own `environment`. Nothing is deployed: the variables and, on Google Cloud, a fake metadata server make serverless-init believe it runs on that platform.

- `local` sets no variables.
- `cloud-run-service` sets `K_SERVICE`, `K_REVISION`, `K_CONFIGURATION` and `PORT`, as Google Cloud Run does for a service.

Every platform named `cloud-run-<kind>` also gets the Compose service `fake-gcp-metadata`, with the network alias `metadata.google.internal`, the host that Go serverless-init asks for the instance ID, the region and the project (`datadog-agent/cmd/serverless-init/cloudservice/cloudrun.go`). The agent starts once its health check passes. It answers `/computeMetadata/v1/instance/id`, `/instance/region` and `/project/project-id` with fixed values (`internal/gcpmetadata`), refuses a request without the header `Metadata-Flavor: Google` with status 403, and returns 404 for any other path. A scenario's `metadata` block selects how it answers: `{mode: answer}`, the default, answers at once; `{mode: slow, delay: 2s}` answers after the delay; `{mode: fail}` returns status 500, after `delay` if one is set.

## Dependency on fakeintake

The capture package uses the fakeintake client, server and aggregator packages. `go.mod` requires `github.com/DataDog/datadog-agent/test/fakeintake` at the placeholder version `v0.0.0-00010101000000-000000000000` and replaces it with `../../datadog-agent/test/fakeintake`, so the local `datadog-agent` checkout must be next to the `serverless-components` checkout. Go ignores the replace directives inside the fakeintake `go.mod`, so `go mod tidy` resolves the modules that fakeintake needs, such as `datadog-agent/pkg/proto`, from the network at released versions. The dependency pulls in `github.com/DataDog/zstd`, which needs cgo, so every package that imports `capture` needs a working C toolchain, such as the capture tests and `cmd/parity`.

On a Mac with the default macOS SDK 27.2, linking fails with `tapi error: unknown architecture` or `malformed file` from `libSystem.tbd`. Point the linker at an older SDK, for example `SDKROOT=/Library/Developer/CommandLineTools/SDKs/MacOSX26.5.sdk go test ./...`. The linker then prints warnings that the object files were built for a newer macOS version; they are harmless.

## Known coverage gaps

These scenarios can't fully test their feature yet, mostly because the workload driver lacks a step. Go against Rust passes them without testing what the name says, so read their result with that in mind.

- `traces.payload-versions-other`: the driver encodes only v0.4 fixtures, so both binaries only record the failed `/v0.5` and `/v0.7` sends on stderr.
- `config.datadog-yaml`: a scenario can't add a `datadog.yaml` to the agent container, so it runs without one.
- `traces.profiling-proxy`: no step posts a profile, so it only sends a trace.
- `process.health-probe` and `traces.info-endpoint`, in part: a failed request shows as a child stderr line, but the HTTP status and the `/info` body are not compared.
- `process.exit-codes` covers only a child exit code (not a missing binary or a child killed by a signal), and `process.argument-splitting` only several arguments (not one quoted argument).
- `logs.stderr-multiline`: stderr log messages reach the intake with a trailing newline, so their delivery delay is not timed; their content is still compared exactly.
- `process.sidecar-mode`: Go flushes only twice before SIGTERM, and a flush interval needs three flushes, so no flush interval is measured; only the delays and the shutdown are timed.
- `process.shutdown-flush` and `process.signal-forwarding`: the workload's metrics fill only two or three 10-second buckets, so `timing.interval.series`, `timing.interval.sketches` and `timing.flush_interval.sketches` are not measurable. A slow DogStatsD path with a normal agent flush is caught only by `timing.max_delay` of series and sketches, and only when a send lands shortly after a flush, so it can pass: `timing.flush_interval.series` cannot see it, because the agent's own metrics keep flushing every 3 seconds.

Each of these scenarios sets `coverage_gap`, so the report marks it. `performance.startup-and-memory` is report-only: its startup time and peak memory are reported next to Go's, but it never passes or fails.

`platform.gcp-metadata-timeout` has no scenario yet. The fake metadata server has `slow` and `fail` modes for it, but only `platform.cloud-run-service` is written, with the server answering at once, so Go's 300-millisecond request timeout and 1.8-second limit are not compared.


## Self-check results

Recorded on 2026-11-22, against the references of serverless-init 1.12.0 (datadog-agent `144c8aebb3a`). The final review's fixes (relative timestamps, references tied to their inputs, three flushes per interval, check runs in the timing check) were followed by a new record on 2026-11-23:

- **Stability** (`stability --runs 3`): all 27 scenarios stable.
- **Go against its own references**: 26 scenarios pass and `performance.startup-and-memory` is reported, `P0 scenarios passing: 21 of 21 (5 with known coverage gaps)`, in 164 seconds.
- **Empty binary**: all 26 compared scenarios fail, none with a harness error, `P0 scenarios passing: 0 of 21`.
- **Slow flush** (the binary described below): four scenarios fail, on timing only: `logs.file-tailing`, `metrics.flush-cadence`, `process.shutdown-flush` and `process.signal-forwarding`, each on `timing.flush_interval.series` and the new `timing.flush_interval.check_runs`. `P0 scenarios passing: 17 of 21`. `process.sidecar-mode` no longer catches it: Go flushes only twice in it, which no longer counts as a measurable interval.

On 2026-11-23 the harness fixes of the phase 3 pilot (project age by container creation time, the late-start check, aligned DogStatsD series timestamps and three more coverage gaps) were followed by a new record of all 27 references with the same Go binary:

- **Go against its own references** (`run --binary go`): 26 scenarios pass and `performance.startup-and-memory` is reported, `P0 scenarios passing: 21 of 21 (8 with known coverage gaps)`, in 171 seconds.
- **Split cadence** (the binary described below, `out/bin/go-split-cadence`): the three timing scenarios that send metrics fail, on timing only, `P0 scenarios passing: 18 of 21 (8 with known coverage gaps)`. `metrics.flush-cadence` fails on `timing.interval.series` and `timing.interval.sketches` (Go 7.1 s, this binary not measurable) and on `timing.max_delay.series` (Go 10.8 s, this binary 19.8 s) and `timing.max_delay.sketches` (25.0 s). `process.shutdown-flush` fails only on `timing.max_delay.sketches` (Go 10.8 s, this binary 19.7 s); its `timing.max_delay.series` was 10.7 s in both. `process.signal-forwarding` fails on `timing.max_delay.series` (Go 10.8 s, this binary 14.0 s) and `timing.max_delay.sketches` (19.8 s). No timestamp label differed.

The results below are from before those fixes. Each modified build came from a temporary worktree of that commit in a directory named `datadog-agent`, used through `PARITY_AGENT_PATH`, and was copied to `out/bin/<label>/datadog-init`.

- **Go against its own references** (`run --binary go`): 25 scenarios pass and `performance.startup-and-memory` is reported. `P0 scenarios passing: 20 of 20 (5 with known coverage gaps)`. The suite took 130 seconds with the default `--parallel 4`, well under the 10-minute target, so `--parallel` is unchanged.
- **Go against its own references, with `platform.cloud-run-service`** (2026-11-23, `run --binary go`): 26 scenarios pass and `performance.startup-and-memory` is reported. `P0 scenarios passing: 21 of 21 (5 with known coverage gaps)`, in 134 seconds. Against the empty Rust binary, `platform.cloud-run-service` fails with no harness error.
- **Slow flush** (`metricsFlushInterval` in `cmd/serverless-init/main.go` set to 10 seconds): the five scenarios whose agent flushes more than once fail on `timing.flush_interval.series`, the interval of all series: `metrics.flush-cadence` (Go 3.0 s, this binary 8.1 s), `process.shutdown-flush` (10.0 s), `process.signal-forwarding` (10.0 s), `logs.file-tailing` (10.0 s) and `process.sidecar-mode` (not measurable). `P0 scenarios passing: 15 of 20 (5 with known coverage gaps)`. The interval of the workload's own metrics hardly moves (7.1 s against 8.1 s), because Go puts them into 10-second buckets either way.
- **Split cadence** (`dogstatsd_packet_buffer_flush_timeout` set to 10 seconds in `cmd/serverless-init/main.go`, so DogStatsD packets wait up to 10 seconds while the agent's own metrics keep the 3-second flush): the three timing scenarios that send metrics fail on the workload's metrics only, for example in `process.shutdown-flush` `timing.max_delay.series` (Go 10.8 s, this binary 19.8 s) and `timing.interval.series` (Go 9.0 s, this binary not measurable). `P0 scenarios passing: 17 of 20 (5 with known coverage gaps)`.
- **Tag removed** (`cmd/serverless-init/tag/tag.go` no longer adds `_dd.compute_stats:1` when `DD_SERVERLESS_INIT_ENABLE_BACKEND_TRACE_STATS` is set; recorded before the alignment change): only `traces.stats-toggles` fails, with four differences, `traces[...].chunk.spans[N].meta[_dd.compute_stats]: Go "1", this binary absent`.
- **Empty binary** (`run --binary rust`, the empty `datadog-init`; recorded before the alignment change): all 26 scenarios fail, none with a harness error, `P0 scenarios passing: 0 of 20`. Each section of the report lists what Go sent and this binary did not.
